Interface design: pages, components, states and device variants

The subject is a browser client that accepts a dependency manifest and presents the dependency tree ranked by the risk that maintenance ceases. The pages that follow document the design of that client: the token foundations, the library of reusable components, the appearance of every interactive element in each state it can occupy, and each screen at five device sizes.

The specimens are rendered by the stylesheets of the application itself rather than drawn, and the screen plates are captures of the running client. A change to a design token therefore reaches this document, which is what keeps a design document and an implementation from diverging. Three appearances are the exception and are noted where they appear: hover, press and keyboard focus cannot be held open in a printed page, so they are reproduced from the rules that produce them.

Foundations: colour

1

One palette, defined once as custom properties and referenced by every component. Each text colour is checked against the surfaces it appears on by a test that fails below the ratio its requirement sets, so the figures below are measurements rather than intentions.

Foundations: type, spacing and target size

2

Every length is relative. A length in pixels would ignore the reader's own font size, and the text scale control in the application would then move the text without moving the space around it.

Screen: submission

8

The entry point. A lockfile is chosen or dropped, and the client refuses what it can refuse locally before a request is made.

  1. Skip link, first in the tab order and visible only when focused.
  2. Brand and primary navigation. Above 48rem it is inline here; below it the bar at the foot carries the same destinations.
  3. The file drop, operable by click, by keyboard and by drag. The accepted name is stated rather than implied.
  4. A local refusal: a file that is not a lockfile is reported here without a request, since the client can tell.
  5. The primary action, disabled until a file is chosen and busy for the duration of the request.
  6. What the service does with the manifest, stated before it is sent rather than in a policy elsewhere.

Screen: report

9

The screen the project exists for: the dependency tree ranked by risk, with the age of the data it rests on and a filter over the entries. It is also the screen whose structure changes most between widths, since a table cannot be narrowed indefinitely.

  1. The permanent link, which is the only copy of the token that is issued.
  2. The age of each source, so a score is read against the data behind it.
  3. Counts: entries submitted, scored, and left unscored with a reason.
  4. The filter, which narrows the tree and has a state of its own when nothing matches.
  5. The ranked tree. The rank is stored with the report, so it is identical on every later read.
  6. The risk badge, carrying the figure, the word and the horizon together.

Screen: entry evidence

10

One entry of a report, with the factors that moved its score, the observed download series and the current assessment of the same package. Above 64rem the evidence sits beside the entry it explains rather than beneath it.

  1. The entry, its version, and its relation to the submitted project.
  2. The factors, ordered by the magnitude of their contribution, so the first is the reason.
  3. The observed download series, which a package has even when its history is too short for a forecast.
  4. A contributor count below the disclosure threshold is withheld rather than rounded, and the screen says which happened.
  5. The current assessment of the same package, which may differ from the stored one and is labelled as current.

Screen: comparison

11

What has changed since the previous assessment of the same manifest, matched on a fingerprint rather than on a stored copy of the file. The first assessment of a manifest has nothing to compare, which is a state of this screen rather than an error.

  1. The two dates being compared.
  2. Entries that appeared, with their first score.
  3. Entries whose score moved, with the direction stated in words.
  4. Entries that are no longer in the manifest.

Screen: registry

12

The list of assessed packages, ranked by risk, for a reader who arrives without a report. Searching matches anywhere in a name and without regard to case.

  1. Search, matching anywhere in a name without regard to case.
  2. Ranked by descending risk, so the first page is the one worth reading.
  3. An unresolved package is listed with the reason it carries no score rather than omitted.
  4. Paging by limit and offset, both repeated in the response, so a page is interpretable on its own.

Screen: method

13

The definition every score rests on, served by the API from the database that holds those scores, so the page cannot disagree with them.

  1. The abandonment definition, in the words the service publishes.
  2. The observation window, and the note that a package still active at its end is right censored rather than called healthy.
  3. The disclosure threshold, below which a contributor count is withheld rather than rounded.
  4. The age of each source, which is what a score should be read against.

The dark theme

14

The theme follows the system preference until the reader chooses otherwise, and the choice persists. It is a second palette rather than an inversion: every pair in it is measured against the same thresholds, which is why the muted text and the risk colours are not the light values lightened.

Device patterns

16

One-handed use and platform patterns. Below 48rem the primary destinations sit in a bar fixed to the foot of the viewport, which is the pattern of Android's bottom navigation and the iOS tab bar and the part of a phone screen a thumb reaches. Exactly one navigation is present at a time, so a reader never meets two. The bar respects env(safe-area-inset-bottom), so it clears a home indicator, and the main content reserves space for it rather than ending underneath.

The on-screen keyboard. The client has two inputs, the file chooser and the filter field. Both sit in normal document flow rather than pinned to the viewport, so a keyboard opening scrolls them into view instead of covering them, and the layout is sized in dvh rather than vh so that the visible height is the one used. No element is fixed to the bottom except the navigation bar, which a keyboard may cover while it is open, when the field being typed into is the thing that matters.

Reader controls. Theme and text scale are the reader's to set, in the appearance control in the header, and both persist. Because every dimension is relative, enlarging the text enlarges spacing, controls and touch targets with it. The end to end suite asserts that doubling the root font size, which is how a browser applies zoom, leaves the phone layout without horizontal overflow.

Accessibility annotations

17

Level AA of WCAG 2.1 is the target. Three of its requirements are checked by tests rather than reviewed, which is why the figures on the colour sheet are measurements.

Requirement How it is met How it is checked
1.4.3 Contrast, minimum Every text colour against every surface it appears on A unit test over the token file, in both themes, at 4.5:1
1.4.11 Non-text contrast Control edges and chart marks The same suite, at 3:1
2.5.5 Target size --touch-target on every control under a coarse pointer Measured in the browser on a phone viewport
1.3.1 Info and relationships The table reflow keeps explicit ARIA roles, since changing display strips a table's implicit semantics Reviewed, and the roles are asserted in component tests
2.4.6 Headings and labels Headings descend without skipping, and a state occupying the whole screen carries that screen's first heading A component test asserts the heading level
2.1.1 Keyboard Every control reachable and operable, with a skip link first in the order Exercised in the end to end suite
2.4.7 Focus visible :focus-visible, so a keyboard reader sees a ring and a pointer user does not Shown on sheet 3, rule mirrored
1.4.1 Use of colour Each risk band carries a numeral and a word, and the chart palette was validated against simulated deuteranopia Reviewed against the simulation
4.1.3 Status messages Loading states are announced politely and failures assertively A component test asserts the live region

Colour is never the sole carrier of meaning. Each risk band is accompanied by a numeral and a word everywhere it appears, so the band survives being read by someone who cannot distinguish the three, and the chart palette separates its two series by hue against blue rather than red against green, a pair that fails simulated deuteranopia.

Two device classes are deliberately out of scope. A foldable is handled as the two widths it presents, since the viewport segment queries are not yet broadly supported, and a smartwatch is not addressed at all: the narrowest layout assumes a readable table of dependency names, which does not fit a display of that size. Both would need a different information design rather than another breakpoint.
